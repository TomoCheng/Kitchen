## 一、專案概述

### 遊戲類型

像素風格(Pixel Art)放置經營遊戲(Idle / Incremental Game)。

### 核心參考

Bongo Cat:強調「按鍵/敲擊」帶來的直覺互動回饋與可愛感,本作將這種節奏敲擊的操作手感,延伸到食材處理與烹調的每個環節。

### 核心賣點(暫定)

- 標準放置遊戲的生產鏈爽感:冰箱 → 砧板 → 鍋子 → 成品,環環相扣、可持續升級。
- **沒有唯一正確的食譜**:同一道菜可以偏酸、偏鹹、偏辣、偏甜或均衡,每條風味路線都能各自追求到 SS 極致——玩家用自己的口味做菜,遊戲機制正式承認每一種風格。
- 錨定食材組合不對玩家公開,「這道菜到底需要什麼」仍需自行實驗發現,保留解謎與收集樂趣。
- 完成菜餚帶有路線詞綴 + 隨機浮動的能力值,驅動 build 養成與雲端排行榜競爭。

### 目標平台

Steam(PC)。

### 目標受眾

放置遊戲愛好者、料理/經營模擬愛好者、休閒向玩家。

### 開發階段

Prototype 開發中:引擎已定案 **Unity + C#**,規劃 13 週/約 170 小時(摘要見第十章,完整規格見技術文件)。

## 二、核心玩法迴圈(v0.4 改版:冰箱訂單制)

> **設計轉向說明**:v0.1 的「食材自動飛向砧板」全自動流,在風味路線系統確立後不再成立——**玩家的調味自主權是整個評分系統的前提**,系統不能替玩家決定煮什麼。核心流程因此定案為「冰箱訂單制」:玩家在冰箱下訂單決定食材組合,生產鏈負責執行。

核心迴圈:冰箱自動產出食材進入庫存 → 玩家下訂單(選食材與數量,介面即時顯示風味加總)→ 食材逐份飛向砧板、按鍵加速處理、處理完即入鍋 → 全數入鍋後玩家按下烹調鈕 → 按鍵加速烹調 → 風味路線評分 → 菜餚紀錄(可存為配方,之後自動重複製作)。

| 階段 | 機制 | 操作方式 |
|---|---|---|
| 冰箱 | 自動產出食材進入庫存;產出間隔與「產出內容的掌控力」皆可升級(見 3.1) | 無需操作(被動) |
| 訂單 | 玩家選定食材與數量,介面即時顯示所選組合的風味加總(見 4.9) | 主動決策——調味的核心 |
| 砧板 | 逐份處理食材,處理完成即邏輯入鍋 | 按任意鍵加速 |
| 鍋子 | 集料;全數入鍋後等玩家按烹調鈕開煮(自動重複時自動開煮) | 按烹調鈕;烹調中按任意鍵加速 |
| 提前烹調 | 烹調鈕隨時可按,只煮鍋內內容,未入鍋者無損退回(見 3.4) | 主動選擇——賭一把 |
| 完成菜餚 | 依風味路線分數判定 Rank,記錄製作者/時間/Rank/路線詞綴;可存為配方 | 無需操作 |

> 設計理由:砧板與鍋子共用同一套「按鍵加速」邏輯,降低學習成本,並讓 Bongo Cat 式的敲擊回饋感貫穿整條生產鏈;同一批次內兩站為先後階段,任意鍵一律加速「當前活動階段」,玩家不需要思考按給誰。「等玩家按烹調鈕」的停頓則是刻意設計——那是玩家對照鍋內風味加總、確認組合的時刻,**按下烹調 = 提交風味謎題的答案**。

## 三、生產鏈系統設計

### 3.1 冰箱(食材產出)──「隨機 → 掌控」成長弧線

**設計原則:隨機本身不是問題,「無法應對的隨機」才是。** 風味路線系統的核心體驗是「我想走某條路線,所以我需要特定食材」,冰箱因此不能停留在純隨機——但完全可控又會讓探索樂趣與升級內容雙雙消失。解法是把「對冰箱的掌控力」本身做成成長線:

| 階段 | 冰箱行為 | 設計目的 |
|---|---|---|
| 開場(前 15~30 分鐘) | 小食材池(5~6 種)純隨機產出 | 池小則隨機亂不到哪去;「有什麼煮什麼」逼玩家嘗試不會主動選的組合,錨定食材的發現不需要教學文案 |
| 早期 | 解鎖**商店**(見 3.5),可花費貨幣立即購買指定食材 | 浮動數值系統從第一道菜就產生「重做」動機,商店是這個動機的安全閥;前期貨幣稀缺,商店天然自我節制,不會架空冰箱 |
| 中後期 | 逐步解鎖**冰箱格子配置**:先「類別格」(此格產出蔬菜類),再升級「指定格」(此格固定產出番茄) | 便宜量產的掌控力,升級樹的主力內容;想走嗜辣系的玩家自己把冰箱配成辣味冰箱,冰箱配置成為 build 表達的一部分 |

- **冰箱 = 生成器 + 庫存,單一實體(已定案)**:原「倉庫」與冰箱庫存合併,容量即冰箱容量(初始 50 起測),擴充 = 付費解鎖冰箱格子——參考圖⑤的上鎖格正好對應此模型。庫存滿時產出暫停(不做溢出丟棄,符合無懲罰調性);被進行中訂單鎖定的食材以標記顯示,不可出售/轉換。
- 本模型同時回答了先前「單一冰箱 vs 多台冰箱」的疑問:採**單一冰箱+多格配置**,每格獨立計時產出。
- 其他升級方向照舊:縮短產出間隔、提升單次產量、食材池擴充、解鎖更多格子。
- 主題呼應:玩家從「有什麼煮什麼」成長到「打理自己的食材庫」,正是一個廚師的成長敘事。

#### 生成中修飾層(隱形體感優化,prototype 直接內建)

- **保底機制**:某食材連續 X 次未出現則強制出現(閾值建議 2 × 池大小起測),消滅「乾旱」挫折。
- **需求加權**:系統提高玩家近期常用食材的出現權重;玩家不會察覺機制存在,只會覺得手感好。
- **訂單加權(v0.4 新增)**:當前訂單的缺料獲得額外權重加成——缺料等待的三個洩壓閥之一,另兩個是提前烹調(3.4)與商店直購缺料(3.5)。
- 此層實作成本極低(純數值邏輯)、體感效益高;所有係數外部化進調試面板。

### 3.2 砧板(食材處理)

- 機制:食材抵達後開始處理,基礎處理時間依等級遞減;一次處理 1 份,批次內逐份進行。
- 操作方式:玩家按下任意鍵時,加速當前活動階段的進度。
- 升級方向:縮短基礎處理時間、提升每次按鍵加速幅度、解鎖「掛機自動加速」。

### 3.3 鍋子(烹調)

- 機制:砧板處理完成的食材邏輯上即刻入鍋(落鍋飛行僅為表現動畫);全數入鍋後等玩家按烹調鈕開煮,烹調中按任意鍵加速。
- **容量(已定案)**:單次訂單/鍋子容量上限 10 份,與 route_cap 基準對齊。
- 批次串行:嚴格一批接一批,烹調中不預切下一批(跨批次流水線列為正式版最佳化)。
- 升級方向:同砧板邏輯(縮短基礎時間、提升加速幅度、掛機自動加速)。

### 3.4 訂單與配方系統(v0.4 新增,已定案)

**單批次流程**:

1. **下訂單**:玩家在冰箱 UI 選定食材與數量並確認;介面即時顯示所選組合的風味向量加總(見 4.9)。確認時鎖定現有庫存,不足部分列為缺口,由後續生成自動補入(配合 3.1 訂單加權)。
2. **逐份供料與處理**:食材一份接一份飛向砧板,按鍵加速;處理完成即邏輯入鍋。
3. **缺料待機**:訂單有缺口且庫存已空 → 生產鏈待機。玩家有三個選擇:等待(訂單加權會提高缺料出現率)、去商店直購缺料、或提前烹調。
4. **開煮(已定案)**:手動訂單於全數入鍋後**等玩家按烹調鈕**才開始;自動重複模式則料齊自動開煮,跳過停頓。
5. **烹調 → 評分 → 完成彈窗**。

**提前烹調(已定案:「鍋內為準」)**:

- 烹調鈕隨時可按(鍋內 ≥ 1 份即啟用),立即以**當前鍋內內容**開煮——鍋內風味加總就是最終評分向量,所見即所煮,零歧義。規則對玩家一句話:「**只有鍋裡的會被煮**」。
- 已離開冰箱但未入鍋者(飛行中、砧板處理中)完整無損退回冰箱庫存(半切狀態不保留);未出發的缺口取消並解除庫存鎖定。
- 風險與趣味:截斷後向量不完整,可能落到另一條路線、甚至錨定失敗——搭配「失敗料理可低價出售」(見 4.6),這是「賭一把」而非懲罰。

**配方自動重複(放置玩法的核心)**:

- 成菜彈窗可「存為配方」;玩家將一條配方設為進行中,料齊即自動連續製作。
- 缺料時顯示缺料圖示、依訂單加權等待;**絕不自動替代食材**——替代等於竄改玩家的調味,違反本作核心信念。
- 敲鍵加速照常生效:自動化只接管「下單與開煮」,不接管「加速」——**主動遊玩與放置掛機並存**,這正是 Bongo Cat 式敲擊感與 idle game 結合的落點。
- Prototype 限 1 條進行中配方;多條並行、離線代煮、「隨便煮」隨機模式列為正式版內容。

### 3.5 食材庫存與補救經濟

隨機產出要成立,前提是「每個產出都有價值」——拿到不要的食材不能是死路。補救管道:

- **庫存**(已與冰箱合併,見 3.1):可堆放、有上限、可付費擴充;刻意**不做腐壞機制**——懲罰壓力與本作溫馨放置的調性不合。
- **轉換**:以有損耗的匯率(建議 3 換 1 起測)將不要的食材轉換成指定食材;建議**限定同風味家族內轉換**(酸味食材之間可互換,酸換辣不行),跨家族取得只能走商店——讓轉換與商店各有定位,並強化風味路線的世界觀。
- **出售**:直接換取貨幣,接回貨幣經濟。

**商店(確定性取得)**:花費貨幣立即購買指定食材,定位是「貴但即時」的救急管道,永遠不該成為量產主力。**缺料直購**:訂單缺料待機時,缺料圖示可一鍵跳轉商店購買該食材——「等待換金錢」,是補救經濟在核心迴圈裡的主要出口。

**經濟鐵律**:三條取得路徑的成本階梯必須始終維持——

> 免費隨機(冰箱)< 有損耗的半指定(轉換)< 花錢全指定(商店)

任何一級倒掛,位於其上的機制就會被玩家永久棄用。轉換匯率也需與「出售再購買」的實質匯率大致對齊,避免出現嚴格優勢路徑。技術文件已將此鐵律寫成自動化測試,每次調數值即自動檢查。

## 四、風味路線與評分系統

### 設計理念:為什麼「自由」不會削弱追求極致的慾望

口味因人而異、因文化而異——這是本作最根本的設計信念。本作刻意不設計一組全體玩家都要收斂到的「唯一正確食譜」,而是讓玩家依照自己的喜好調味,並透過遊戲機制正式承認這些不同風格都值得被追求到極致。

這個方向容易引發一個疑慮:如果沒有「絕對正確」,玩家還會有動力衝 SS 嗎?答案是會的,前提是把「沒有絕對答案」正確地翻譯成「**有很多個答案,每一個都值得追求到極致**」,而不是「怎麼做都差不多、無所謂」。這在其他遊戲類型早已被驗證過:動作 RPG(如暗黑破壞神、流亡黯道)裡沒有「唯一最強 build」,火法師、冰法師、近戰玩家各自都能把角色練到頂,但每一條路線內部依然有清楚的「這條路線的天花板長怎樣」。玩家不會因為「build 很自由」就不想把角色練滿,反而正是這份自由,讓更多玩家找到自己真正想追的那個頂點——選擇路線本身,就是一種自我表達;把選定的路線走到極致,才是真正的挑戰所在。

番茄炒蛋也是同樣的邏輯:沒有「唯一的番茄炒蛋」,但「你的酸香番茄炒蛋能不能純粹又濃郁到 SS」依然是一個明確、值得追求的目標。以下「身分核心」與「風味路線系統」的設計,就是把這個信念落地成具體的計分機制。

### 4.1 身分核心(錨定食材)

- 每道菜由 1~2 組「錨定食材類別」決定基本身分(例如番茄炒蛋需要蛋類食材+番茄/番茄醬類食材);錨定採「每組都要滿足、組內任一類別命中即可」的結構。
- 錨定內容只存在於資料層、不在任何 UI 顯示——天然滿足「不對玩家公開」,需自行實驗發現,這是保留下來的「食譜探索」樂趣所在。
- 多道菜同時命中錨定時,取定義最嚴格者(specificity 最高)——例如「番茄炒蛋」優先於假想的泛用「炒蛋」。
- **錨定失敗的處理(已定案)**:不符合任何菜餚錨定時,不採「全損失敗」——放置遊戲裡「產出 = 0」的挫折感過重,且違反 3.5「每個產出都有價值」原則。生成一筆灰色「失敗料理」紀錄:只能低價出售(如固定 5 金)、不進圖鑑、無詞綴——實驗的成本是「賺得少」,不是「全部白費」。

### 4.2 風味軸(已定案:五軸)

食材各自帶有風味貢獻值,累加後形成本次嘗試的風味向量。風味軸:**酸、甜、苦、鹹、辣**——辣已正式定案為第五軸(資料層成本為零;若實測嗜辣系不好玩,拔掉也只是改資料)。

**風味值採整數(刻意的設計決策)**:整數 + 路線上限(cap)的組合,會讓 SS 變成一道**離散解謎題**——「找出一組食材,主導軸剛好加總到 cap、其餘軸全壓在幫襯範圍內」,有唯一或少數幾組解,完美對應「衝 SS」的追求感。這是設計價值,不是實作偷懶。

**苦味定位(已定案):純干擾軸**——苦沒有對應的特化路線,苦味食材的角色是「雜訊挑戰」:誤入鍋中會壓低純度與均勻度。為了讓這個軸在 prototype 真實存在,起始食材池包含苦瓜(見附錄 A)。

### 4.3 風味路線與主導軸判定

通過錨定判定後,系統依風味向量自動分類:

- **主導軸判定(數值已定案)**:最高軸值 ≥ **1.35** ×(第二高軸值)→ 進入該軸對應的特化路線;否則進入均衡系。兩軸同值必然不過門檻,自動落入均衡系,無需特例。門檻由 1.25 上調至 1.35(經模擬工作台調校):判定更嚴,「副軸跟得太緊」的組合會被推入均衡系,特化身分更難拿、更有價值。

| 路線 | 判定 | 說明 |
|---|---|---|
| 酸香系 | 酸味主導 | |
| 鮮鹹系 | 鹹味主導 | |
| 嗜辣系 | 辣味主導 | 辣已定案為第五軸(4.2) |
| 微甜系 | 甜味主導 | |
| 均衡系 | 無明顯主導軸 | 不代表清淡無味,而是照顧飲食控制/清淡口味玩家的**正式路線**,與其他路線平起平坐 |

### 4.4 計分邏輯

- **特化路線**:`分數 = 純度 × 強度`(數值已定案)
  - 強度 = 主導軸值 ÷ 該菜該路線的上限(route_cap,基準 **10**、逐菜可調);**超標懲罰於 prototype 即開啟**:超過 cap 後線性扣分、達 2×cap 歸零。模擬顯示「封頂不罰」會讓 69% 的 SS 靠無腦堆料達成、解謎崩壞,故推翻技術文件「正式版再議」的原判斷。
  - 純度:每個非主導軸與主導軸的比值 ≤ **0.45** 視為「幫襯」不扣分;超過即線性衰減(衰減寬 **0.6**,比值約 1.05 時歸零)。整體純度取最搶戲的那一軸決定。
- **均衡系**:`分數 = 均勻度 × 適中度`(數值已定案)
  - **計算軸範圍(已定案)**:只計算該菜授權路線涉及的風味軸,而非全部五軸——否則任一軸為 0 就會把均勻度打成零,等於強迫番茄炒蛋加苦瓜才能走均衡系。改用授權軸既合理又是資料驅動。
  - 均勻度 =(各計算軸中最低值 ÷ 最高值)**開根號**——未開根號時整數顆粒過粗,S 與 B 區間會整段空掉(模擬驗證)。
  - 適中度 = 各計算軸平均值落在「適中區間」(balanced_band,基準 **2.5~6.5**、逐菜可調)內為滿分,區間外線性衰減(衰減寬 **1.5**)——不會清淡到近乎無味,也不會濃到跟特化路線一樣重口味。

### 4.5 範例:番茄炒蛋(v0.5 依定案數值重寫)

以下三個配方構成一道漂亮的階梯(route_cap = 10,食材數值見附錄 A):

- **蛋×1+番茄×2+檸檬×2** → 酸 10(= cap)、甜 2(比值 0.2,幫襯)→ 純度 1 × 強度 1 = **100% → SS**。
- **蛋×1+番茄×5** → 酸 10、甜 5(比值 0.5 > 0.45,純度 0.917)→ **91.7% → S**。
- **蛋×1+番茄×4** → 酸 8、甜 4(純度 0.917 × 強度 0.8)→ **73.3% → B**。

三者都是「番茄+蛋」:靠檸檬把酸推滿又幾乎不帶雜味 = SS;純堆番茄能推滿酸、但甜跟著上來 = S;推不滿 = B——**「找到把主導軸剛好推到 cap、又不帶進多餘雜味的組合」就是每條路線的 SS 解謎**。

另外,v0.4 的舊範例(蛋×2+番茄×3+糖×1+鹽×1,酸 6 甜 5 鹹 2)在門檻 1.35 之下已不構成酸味主導(6 < 1.35 × 5),會落入均衡系拿 57.7% C——正好展示門檻收緊後「副軸跟太緊就不算特化」的效果。

> 沿革:v0.3 範例與公式矛盾,v0.4 修正,v0.5 依定案參數全面重算。

### 4.6 Rank 對應區間(v0.4 修正)

| Rank | 分數 | 說明 |
|---|---|---|
| SS | ≥ 99.5% | 「= 100%」的浮點安全版;整數風味設計下 = 找到該路線的離散完美解 |
| S | 90% ~ 99.5% | |
| A | 75% ~ 90% | |
| B | 60% ~ 75% | |
| C | < 60% | 已定案:C 仍算成菜——可出售、進圖鑑,與錨定失敗的「失敗料理」(見 4.1)明確區隔 |

> **分布快照(定案參數,9 食材、鍋容量 10、窮舉 92,368 種組合)**:特化路線 SS 5.5%(471 組、全為正當解、堆料 SS = 0)/ S 10.9% / A 16.8% / B 24.9% / C 42.0%;均衡系 SS 5.3% / S 6.8% / A 13.6% / B 23.6% / C 50.7%。全區間有效佔用,先前的 S 區間空洞與堆料漏洞皆已解除(Q5 結案)。食材池變動時需以模擬工具重跑快照。

### 4.7 路線授權(內容設計指引)

- 並非每道菜都開放全部 5 條路線,由設計師逐菜決定(例如甜點類不需要「鹹味主導」路線),避免「鹹味冰淇淋 SS」這種不合理組合。
- 落地方式(已定案):每道菜的資料定義包含授權路線清單、各路線上限(route_cap)、均衡區間(balanced_band)——全部資料驅動,設計師改 JSON 即可,不動程式。
- **未授權路線的處理(已定案)**:被判定為未授權特化路線的鍋(例如甜味主導的番茄炒蛋)固定判 **C 級成菜**——可出售、不記入圖鑑的路線紀錄。定案參數的窮舉中約有 5,362 鍋屬此類,佔比不小,「不全損」很重要。

### 4.8 wiki 防護的優先順序調整

因為「查攻略」在此設計下比較接近「查 build 攻略」而非「看破解答案」,對遊戲性的傷害相對較低。因此先前規劃的賽季目標重洗+個人隨機偏移機制,調整為【**未來可選加強項**】,不列入 prototype 必做範圍,待正式上線後依實際社群行為觀察是否需要加開。

### 4.9 資訊揭露原則(已定案)

- **揭露**:玩家在訂單 UI 與鍋內,即時看到「自己這次組合的風味加總」——這是解謎的操作介面。看得到自己的答案卷,按下烹調 = 提交答案。
- **不揭露**:各菜的錨定食材、route_cap、balanced_band 等目標參數——探索標的仍然隱藏,「這道菜的酸要推到多高才是極致」得靠玩家自己逼近。
- 正式版再議揭露程度(例如數字 vs 純圖形化呈現)。

## 五、完成菜餚與紀錄系統

每道完成的菜餚會記錄:製作者名稱(prototype 為本地暱稱,正式版換 Steam 名稱,欄位不變——見第八章)、製作時間、Rank(依路線分數判定)、風味路線。

### 5.1 菜名與路線標示

完成菜餚的顯示名稱會加上路線前綴,例如「**酸香番茄炒蛋 · SS**」而非單純「番茄炒蛋」,讓玩家的個人風格直接寫在結果畫面上——這是把「沒有唯一正確答案」的理念最直白傳達給玩家的方式。

### 5.2 Tier + 浮動數值系統

- Rank 決定該次製作獲得的能力值 Tier(數值大小),對應關係(示意,待實測):

| Rank | Tier | 詞綴數值範圍(示意) |
|---|---|---|
| SS | 5 | +10% ~ +14% |
| S | 4 | +7% ~ +10% |
| A | 3 | +5% ~ +7% |
| B | 2 | +3% ~ +5% |
| C | 1 | +1% ~ +3% |

- 風味路線決定詞綴「種類」,與 Tier 互相獨立:酸香 → 酸味食材加成、鮮鹹 → 鹹味加成、嗜辣 → 辣味加成、微甜 → 甜味加成;**均衡系 → 通用型詞綴(生產速度或金幣加成,二擇一隨機)(建議,待確認)**——讓均衡系握有人人想要的泛用加成,確保「與其他路線平起平坐」不是口號。
- 同一 Tier 內,實際數值於範圍內均勻隨機浮動,生成即寫入紀錄、永久鎖定 → 重製賭值的動機成立。
- 失敗料理(4.1)不產生詞綴。

### 5.3 菜餚圖鑑(Compendium)

收錄玩家已發現的所有菜色,並**依路線分別記錄最佳 Rank**(例如番茄炒蛋的酸香系/鮮鹹系/均衡系……各自最佳紀錄),鼓勵玩家嘗試同一道菜的不同風格,作為長線收集目標。

- **建議(待確認)**:未授權的路線在詳情面板顯示鎖定圖示——暗示玩家「這道菜沒有這條路」,降低無效嘗試的挫折。

## 六、能力值與進度系統

### 6.1 裝備式被動加成

- 玩家有限的展示欄位(prototype 3 格起步,資料結構支援 5 格,後 2 格顯示鎖定)。
- 可將手上菜餚「擺盤」進欄位,提供持續被動加成;同類詞綴加法疊加(prototype 從簡)。
- 詞綴種類由風味路線決定(見 5.2),玩家可依當下需求(衝升級/衝貨幣/衝特定路線)組合不同菜餚,形成小型 build-crafting 玩法。

### 6.2 路線專精與稀有食材解鎖【正式版內容,prototype 不做】

- 玩家持續在某條路線取得高分,逐步解鎖該路線的稀有食材(例如嗜辣系解鎖特級辣椒、陳年辣醬)。
- 稀有食材本身風味貢獻值更高,讓專精玩家能把該路線走得更極致,形成「越愛辣、越能把辣走到極致」的正向循環。
- **待確認**:解鎖門檻(需要多少次高分紀錄或累積分數)需要實測調整。

### 6.3 總分/排行榜

裝備組合總值或歷代最佳 Rank 換算為「廚房評分」;prototype 以集中式純函式計算並在本地顯示,正式版同一數字上傳 Steam 雲端排行榜(見第八章預留接口)。

### 6.4 貨幣經濟

- 貨幣來源:出售完成菜餚、出售多餘食材(見 3.5)。
- 貨幣去向(gold sink):升級冰箱/砧板/鍋子效率、解鎖與升級冰箱格子(= 擴充容量)、商店購買指定食材(含缺料直購)。
- **菜餚售價與 Rank/Tier 掛鉤(已採納,數值待實測)**:`售價 = 基礎價 × Rank 倍率 ×(1 + Tier × 0.05)`,Rank 倍率起測值 SS 3.0 / S 2.2 / A 1.6 / B 1.2 / C 1.0;失敗料理固定低價(如 5 金)。「做得越好、賺得越多」的正向回饋成立。

## 八、平台與線上功能(Steam)

目標平台為 Steam(PC)。**Prototype 已定案:Steamworks runtime 零整合**——整合工時(25~40 小時)驗證不了 prototype 的任何核心問題,全數移出;改以四個零相依的預留接口(合計約 4 小時)保住正式版接線路徑,正式版整合估 3~5 個工作天,屬「接線」而非「重構」:

- **雲端存檔就緒**:固定路徑單一 JSON 存檔 + 版本欄位;正式版由 Steam 後台 Auto-Cloud 同步,零程式碼。
- **玩家身分介面**:prototype 回傳本地暱稱(設定頁輸入一次),正式版換 Steam 名稱,呼叫端不動。
- **廚房評分函式**:集中式純函式計算、本地顯示;正式版同一數字上傳排行榜。
- **統計服務**:累計統計(首次 SS、累計成菜數、圖鑑完成率等)寫入存檔;正式版成就 = 統計門檻 → API 呼叫的映射表。

正式版線上功能規劃不變:雲端存檔、雲端排行榜(廚房評分、單一菜色各路線最佳 Rank)、成就系統(「首次做出 SS Rank」「同一道菜集滿全部路線 S 以上」「集滿圖鑑 50%」等——路線系統天然提供成就素材)。

### 離線進度(v0.4 更新)

- **離線只結算冰箱產出,不自動做菜**——配方自動重複僅在遊戲開啟時運作(離線代煮列為正式版再議)。這與「玩家調味不可代勞」的設計自洽,實作也簡單一個數量級。
- 結算:60% 效率、上限 10 小時起測,逐一抽選(沿用 3.1 生成器)放入庫存、滿即止;回到遊戲顯示「離線期間冰箱補了 N 樣食材」小結算窗。

## 十、Prototype 開發規劃(摘要,完整版見技術文件)

### 驗證目標:Prototype 只回答三個問題

1. **敲擊手感**:Bongo Cat 式按鍵加速貫穿砧板+鍋子,玩起來爽不爽?
2. **風味路線系統**:「實驗 → 發現錨定食材 → 挑路線衝 SS」這條樂趣鏈成不成立?
3. **經濟循環**:賣菜 → 升級 → 產得更快更好,循環有沒有推進感?

明確不驗證:Steam 線上功能、內容量、美術完成度、長線留存。

### 資源與範圍

- 每週約 15.5 小時,13 週合計約 **170 小時**可用;引擎 **Unity + C#**。
- **Must**:核心生產鏈+訂單制、按鍵加速、評分全套、完成彈窗、紀錄+詞綴、貨幣+出售+基礎升級、本地存檔。
- **Should**:圖鑑、展示欄、食材商店(含缺料直購)、容量擴充、生成修飾層、調試面板。
- **Could**:冰箱類別格(最簡版)、食材轉換、離線產出。
- **Won't**:Steam runtime 整合(改預留接口)、指定格、路線專精、賽季重洗、正式美術與音效。

### 里程碑(13 週)

| 里程碑 | 週次 | 內容 | 可玩驗收 |
|---|---|---|---|
| M0 | 1 | 專案建置、資料層、事件系統、存檔骨架 | 讀得到資料 |
| M1 | 2~4 | 冰箱訂單 → 砧板 → 鍋子全流程、提前烹調、按鍵加速 | 能以訂單做出一道菜,敲擊有感 |
| M2 | 5~6 | 評分全管線、完成彈窗、詞綴 | 同一道菜能做出不同路線不同 Rank |
| M3 | 7~8 | 出售、升級、商店、擴容、成本階梯測試 | 金幣循環轉得起來 |
| M4 | 9~10 | 圖鑑、展示欄、配方自動重複、修飾層、調試面板 | 掛著會自己煮 |
| M5 | 11~13 | 存檔完善、離線產出、數值平衡、打磨、緩衝 | 30 分鐘完整遊玩不壞檔 |

**關鍵原則**:M1 是手感驗證點——如果敲擊不好玩,問題要在第 4 週暴露而不是第 12 週;每個里程碑結尾都是可玩狀態;Could 級只在緩衝有剩時做。
